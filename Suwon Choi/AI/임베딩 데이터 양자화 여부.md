# 💾 Vector DB 양자화(Quantization) 도입 전략

초기 구축 단계(MVP)에서 임베딩 벡터 저장 시 **양자화(Quantization) 옵션 적용 여부**에 대한 기술적 의사결정 가이드입니다.

## 1. 핵심 결론 (TL;DR)

> 💡 지금은 적용하지 마세요 (Do Not Quantize yet).
초기 단계(작품 수 5만 개 미만)에서는 원본 데이터(Float32)를 그대로 사용하는 것이 개발 생산성과 추천 정확도 면에서 유리합니다. 양자화는 데이터 규모가 10만~50만 건을 넘어가는 시점에 도입하는 것이 정석입니다.
> 

---

## 2. 양자화(Quantization)란?

데이터의 정밀도를 낮춰 **용량을 줄이고 속도를 높이는 압축 기술**입니다.

- **Float32 (원본):** `0.123456...` (4 byte) → 정밀하지만 무거움.
- **Int8 (양자화):** `12` (1 byte) → 가볍지만 미세한 정보 손실 발생.
- **효과:** 메모리 사용량 1/4 ~ 1/10 감소, 검색 속도 향상.
- **단점:** 추천 정확도(Recall) 미세 하락.

---

## 3. 서비스 단계별 판단 기준

현재 프로젝트 상황(MVP/초기)에 비추어 볼 때, **1단계** 전략을 따르는 것을 권장합니다.

### ✅ 1단계: 초기 & MVP (< 50,000 items)

- **전략:** **양자화 미적용 (Float32 유지)**
- **이유:**
    1. **용량 문제 없음:** 512차원 벡터 5만 개는 메모리 **약 100MB** 수준으로, 현대 서버 스펙에서 무시할 만한 크기입니다.
    2. **정확도 우선:** 초기 유저에게는 가장 정확한 결과를 보여주는 것이 중요합니다.
    3. **복잡도 제거:** 개발 단계에서 양자화 파라미터 튜닝에 시간을 쏟을 필요가 없습니다.

### 🔜 2단계: 성장기 (> 500,000 items)

- **전략:** **Scalar Quantization (SQ8) 도입**
- **이유:**
    1. 메모리 비용 절감이 유의미해지는 시점입니다. (약 1GB → 250MB)
    2. SQ8은 정확도 손실이 거의 없으면서(99% 유지) 메모리를 1/4로 줄여주는 **가성비 최고의 구간**입니다.

### 🚀 3단계: 유니콘/대규모 (> 10,000,000 items)

- **전략:** **Product Quantization (PQ) + Re-ranking**
- **이유:**
    1. 메모리에 다 올릴 수 없는 수준이므로 강력한 압축(PQ)이 필수입니다.
    2. 떨어진 정확도를 보완하기 위해 **2단계 검색(Re-ranking)** 구조를 사용합니다.

---

## 4. 미래를 위한 아키텍처: Re-ranking 전략

## 4. 미래를 위한 아키텍처: Re-ranking 전략

나중에 양자화를 도입할 때, **"속도"와 "정확도"를 모두 잡기 위해** 사용하는 표준 패턴입니다.


```
graph TD
    subgraph Vector_DB [1. 1차 검색 (속도 중심)]
        Query[유저 벡터] -->|검색| Index[양자화된 인덱스 (Int8)]
        Index -->|빠르지만 부정확| Top200[Top 200 후보 추출]
    end


    subgraph Memory [2. 데이터 조회]
        Top200 -->|ID 조회| RawVec[원본 벡터 가져오기 (Float32)]
    end

    subgraph Re_Rank [3. 2차 정렬 (정확도 중심)]
        RawVec -->|정밀 계산| Calculate[정확한 점수 재계산]
        Calculate -->|Sort| FinalTop[최종 Top 50 추천]
    end
```

1. **Search (검색):** 양자화된 벡터로 빠르게 후보 200개를 긁어옵니다. (약간의 오차가 있어도 괜찮음)
2. **Rescore (재계산):** 뽑힌 200개에 대해서만 **원본(Float32) 벡터**로 점수를 다시 계산하여 순서를 바로잡습니다.
