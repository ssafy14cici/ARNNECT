# Redis 추천 캐싱 설계 정리

## 1. Redis를 사용하는 목적

- AI 추천 호출 비용/지연 최소화
- 새로고침 시 **즉시 응답**
- “완전 실시간”이 아닌 **체감상 실시간 추천** 제공

> Redis는 추천 결과 캐시 역할이며,
> 
> 
> 로그 처리·학습 데이터는 담당하지 않음
> 

---

## 2. Redis에 저장하는 데이터

### 사용자별 추천 결과

- 저장 내용: **작품 ID 리스트 (예: 50개)**
- Key 예시:

```
recommend:user:{userId}

```

### 저장 형태

- List 또는 Sorted Set
- 정렬 기준:
    - click 가중치 ↑
    - exposure 가중치 ↓
    - 이후 **가중 랜덤 추출**

---

## 3. Redis 저장 시점 (핵심)

### ✅ 저장 트리거 = AI 호출 직후

Redis는 **사전 적재하지 않음**

### 저장되는 경우

- 최초 페이지 접근
- Redis miss
- TTL 만료
- 취향 변경(흑백 선택 등)

```
요청 발생
 → Redis 조회
   → miss
     → AI 서버 호출
       → 결과 수신
         → Redis 저장(+TTL)

```

---

## 4. Redis miss 시 대응 전략

### 기본 원칙

- **초기 1회 느린 응답은 허용**

### UX 방어책

- AI 응답 지연 시:
    - 인기 작품 / 최신 작품 / 랜덤 fallback 응답
    - AI 결과는 백그라운드에서 Redis에 저장

---

## 5. TTL 전략 (이분법 아님)

### ❌ 잘못된 접근

- TTL 짧으면 좋다 / 길면 나쁘다

### ✅ 권장: 데이터 성격별 TTL 분리

### 사용자 추천 결과

```
TTL: 5 ~ 10분

```

- 새로고침 여러 번 → Redis 사용
- 짧아도 시스템 부담 없음

### 전역 후보군(인기/랜덤)

```
TTL: 1 ~ 5분

```

### 사용자 행동 집계 데이터

```
TTL: 6 ~ 24시간

```

---

## 6. 추천 다양성 확보 전략

### 노출·클릭 기반 보정

- 노출 시: exposure_count +1
- 클릭 시: click_count +k (k > 1)

### 점수 예시

```
score = (click_count × α) − (exposure_count × β)

```

### 조회 시

- 상위 N개 중 **가중 랜덤 선택**
- 동일 작품 반복 노출 방지

---

## 7. “실시간 반영”에 대한 정리

- 로그 수집: **실시간**
- 추천 결과 반영: **지연 허용**

> 클릭 직후 추천이 바뀌지 않아도 UX 문제 없음
> 
> 
> 5~10분 지연은 정상 범위
> 

---

## 8. 핵심 결론

- Redis는 **항상 최신 데이터**가 목적이 아님
- **짧은 시간 동안 신뢰 가능한 캐시**
- AI 호출은 “필요할 때만”
- 추천 품질보다 **안정성과 응답 속도 우선**
