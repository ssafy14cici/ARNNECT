# 파이프라인 설계

## 프로젝트 전제

- 개발 기간: **3주**
- 규모: **소규모 / 학습·프로젝트용**
- 아키텍처: **모놀리식(Spring Boot 중심)**

---

## 핵심 의사결정 기준

### ❗ 가장 중요한 기준

> 실시간성이 반드시 필요한가?
> 
- 즉시 반영 필요 → Kafka
- 몇 분 지연 허용 → Batch / Micro-batch

---

## 실시간 vs 지연 허용의 차이

### 실시간 처리 (Kafka)

- 사용자 행동 직후 추천 결과 즉시 반영
- 예: 숏폼 피드, 실시간 콘텐츠 추천
- ms~초 단위 처리

### 지연 허용 처리 (Batch / Micro-batch)

- 수 분 단위 반영
- 예: 개인화 추천, 인기 콘텐츠, 랭킹
- 사용자 UX에 큰 문제 없음

---

## 마이크로 배치란?

- **1~5분 주기**로 배치를 실행하는 방식
- 체감상 거의 실시간

```
1분 / 3분 / 5분 주기 Batch
```

---

## Kafka vs Micro-batch 비교

| 항목 | Kafka | Micro-batch (Spring Batch) |
| --- | --- | --- |
| 실시간성 | 매우 높음 | 분 단위 |
| 개발 난이도 | 높음 | 낮음 |
| 인프라 | 무거움 | 가벼움 |
| 운영 부담 | 큼 | 작음 |
| 3주 프로젝트 적합성 | ❌ | ✅ |

---

## 추천 아키텍처 (현재 프로젝트 기준)

```
Client
 ↓
Spring Boot API
 ↓
event_log (MySQL)
 ↓ (1~5분)
Spring Batch Job //이 부분은 AI 서버에서 어떤 데이터를 필요로 하는가에 따라 달라짐
 ├─ 행동 집계
 ├─ 추천 점수 계산
 └─ Redis / 집계 테이블 저장

```

### 포인트

- event_log를 **이벤트 기반 구조**로 설계
- 나중에 Kafka로 전환 시 메시지 포맷 그대로 재사용 가능

---

## Kafka를 쓰는 진짜 이유

- 단순 성능 문제가 아님
- **확장성과 구조적 분리(Decoupling)**

### Kafka 장점

- Producer(API)와 Consumer(추천/통계/학습) 완전 분리
- Consumer 추가 시 기존 코드 무변경
- 장애 격리 및 재처리 용이

---

## Micro-batch의 한계

- 완전 실시간은 아님 → 추천 시스템 데이터 캐싱처리에서 실시간 관련 지연문제로 캐싱(완전 실시간x)
- 배치 실행 시간이 길어지면 주기 관리 필요
- 중복/누락 처리 로직 필요 (배치 재실행, 장애대응)

---

## 의사결정 체크리스트

- 추천 결과가 **즉시** 바뀌어야 하는가? 호출 지연으로 인해 레디스로 캐싱할거임, 즉시 아니어도 될듯
- 5분 후 반영돼도 UX에 문제가 없는가? 취향이 너무 큰 폭으로 변화되지않을거임
- Kafka 운영 경험/시간이 있는가? O 근데 시간은 없음

➡️ 하나라도 부담되면 **Spring Batch + Micro-batch 선택이 합리적**
