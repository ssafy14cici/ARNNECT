# Recommendation Service (Serving Repository)

## 1. 이 저장소의 목적

이 저장소는 **이미 학습이 완료된 추천 모델을 실제 서비스로 제공하기 위한 서빙 전용 저장소**입니다.

이 저장소의 역할은 다음과 같습니다.

- 학습된 추천 모델(`.pth`)을 로드하여 추론 수행
- 실시간 추천 API 제공
- 신진 예술가 노출, 다양성, 정책 필터링 등의 **후처리 로직 적용**
- 추천 결과 로그 수집 및 운영 지표 생성

❌ 모델 학습  
❌ 데이터 수집 / 전처리  

위 작업은 **다른 저장소에서 수행**하며,  
이 저장소는 **“학습 이후 → 실제 서비스” 단계만 담당**합니다.

---

## 2. 전체 추천 서비스 흐름


핵심 개념:

- 모델은 **유저의 취향을 계산**하는 역할만 담당
- 비즈니스 목표(신진 노출, 공정성 등)는 **후처리 레이어에서 제어**

---

## 3. 서빙 전 필수 준비 사항 (오프라인 산출물)

### 3.1 아이템 벡터 사전 (필수)

모든 작품에 대해 **아이템 벡터를 미리 계산**해 둡니다.

- 각 작품 → `v_item (512-dim vector)`
- 실시간 요청 시 모델을 다시 돌리지 않기 위함
- 추천 속도 및 서버 비용 절감 목적

저장 방식:

- 아이템 수 1만 이하: 파일 또는 메모리 로드
- 규모 확장 시: 벡터 DB (FAISS / Milvus / Redis Vector 등)

---

### 3.2 유저 벡터 생성 전략

유저 벡터(`u`)는 다음 중 하나의 전략으로 관리합니다.

#### 권장 (MVP)

- 사용자 행동 발생 시:
  - personality_vector 갱신
  - 유저 벡터 `u`를 캐시에 저장
- 추천 요청 시:
  - 캐시된 `u`를 즉시 사용

→ 실시간 성능과 구현 난이도의 균형이 가장 좋음

---

## 4. 실시간 추천 API 파이프라인

### 4.1 추천 갱신 트리거

추천을 언제 다시 계산할지 정의합니다.

권장 기준:

- 페이지 진입(View)
- 좋아요 / 댓글 / 공유 등 **강한 사용자 행동**

모든 이벤트마다 갱신 ❌  
의미 있는 이벤트만 갱신 ⭕  

---

### 4.2 후보 생성 (Recall)

현재 기준: **아이템 수 ≤ 10,000**

#### MVP 방식

- 모든 아이템에 대해 점수 계산
- `score = u · v`
- Top-K 선택

장점:

- 구현 단순
- 디버깅 용이

※ 아이템 수 증가 시 ANN(FAISS 등)으로 교체 가능

---

### 4.3 후처리 / 정책 레이어 (중요)

후처리는 **모델 점수 위에서 작동하는 비즈니스 로직**입니다.

주요 역할:

1. **신진 예술가 가산점**
   - 업로드 후 N일 이내
   - 팔로워 수가 적을수록
   - 당일 노출 수가 적을수록

2. **과다 노출 / 중복 방지**
   - 동일 작가 연속 노출 제한
   - 유사 스타일 연속 노출 방지 (다양성)

3. **정책 필터링**
   - 신고 / 차단 / 성인 / 저작권 콘텐츠 제거

이 레이어를 통해  
**신진 작품 노출 비율(예: 20~30%)을 안정적으로 제어**합니다.

---
