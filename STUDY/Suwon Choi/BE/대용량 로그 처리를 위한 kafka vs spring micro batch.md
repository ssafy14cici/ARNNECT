# 🛠️ [기술 검토] 대용량 로그 처리를 위한 Kafka vs Spring Micro Batch

## 1. 개요
추천 시스템을 위한 사용자 행동 로그(Interaction Log)는 양이 방대하고 지속적으로 발생합니다. 이 데이터를 유실 없이 수집하고 분석 가능한 형태로 가공하기 위해 고려되는 두 가지 핵심 기술인 **Apache Kafka**와 **Spring Micro Batch**를 비교 분석합니다.

---

## 2. Apache Kafka (아파치 카프카)
> **한줄 정의:** 데이터가 쏟아져 들어오는 거대한 고속도로 (분산 이벤트 스트리밍 플랫폼)



### 📌 핵심 개념
* **Pub/Sub 모델:** 데이터를 보내는 측(Producer)과 받는 측(Consumer)이 독립적으로 소통하는 구조입니다.
* **고성능 & 고가용성:** 초당 수십만 건의 이벤트를 처리하며, 서버 장애 시에도 데이터 유실을 방지합니다.
* **디스크 저장:** 메시지를 디스크에 보관하여 장애 발생 시 데이터를 재처리(Replay)할 수 있습니다.

### 👍 장점
1. **실시간성:** 데이터 생성 즉시(ms 단위) 소비 및 처리가 가능합니다.
2. **안정성:** 수집 서버와 처리 서버의 속도 차이를 조절하는 완충지대 역할을 합니다.

### 👎 단점
1. **운영 비용:** 인프라 구축 및 관리가 복잡하며 별도의 서버 자원이 필요합니다.
2. **학습 곡선:** 분산 시스템에 대한 높은 이해도가 요구됩니다.

---

## 3. Spring Micro Batch (스프링 마이크로 배치)
> **한줄 정의:** 쌓인 데이터를 삽으로 퍼서 부지런히 나르는 일꾼 (초단기 일괄 처리)



### 📌 핵심 개념
* **Chunk 지향 처리:** 대량의 데이터를 설정한 크기(Chunk)만큼 쪼개서 읽고 가공하고 기록합니다.
* **Micro Batch:** 배치를 아주 짧은 주기(예: 30초, 1분)로 실행하여 실시간성을 확보하는 전략입니다.

### 👍 장점
1. **안정적인 트랜잭션:** 대량의 DB 반영 작업 시 데이터 정합성을 보장합니다.
2. **개발 용이성:** 별도 인프라 없이 Spring 환경에서 즉시 구현 가능합니다.

### 👎 단점
1. **지연 시간:** 배치가 실행되는 주기만큼 데이터 반영이 늦어집니다.
2. **부하 발생:** 주기적으로 DB를 조회(Polling)하므로 데이터가 없어도 리소스를 사용합니다.

---

## 4. 기술 비교 요약

| 구분 | **Apache Kafka** | **Spring Micro Batch** |
| :--- | :--- | :--- |
| **주요 역할** | 데이터 **전송 및 버퍼링** | 데이터 **가공 및 적재** |
| **처리 방식** | 이벤트 스트리밍 | 스케줄링 기반 일괄 처리 |
| **실시간성** | 매우 높음 | 중간 (배치 주기만큼 지연) |
| **구축 난이도** | 높음 (인프라 필요) | 낮음 (코드 구현 위주) |

---

## 5. 기술 선택 기준
RDB와 Kafka를 선택하는 기준은 여러 가지가 있다.
1. TPS
2. 사용자 응답 속도 느려짐
3. 로그의 용도가 많아짐 (Fan-out)
4. 실시간성 요구사항이 중요해짐

- TPS의 경우는 100~500 TPS 이내로 예상되므로 RDB로 충분히 수용 가능할 것으로 예상됨
- 사용자 응답 속도는 실제 테스트를 바탕으로 Latency가 얼마나 생기는지 측정을 해보고 결정
- 로그의 용도는 일단 추천 시스템에만 사용하므로 다양하지 않음
- 실시간성의 경우는 Redis를 사용하여 실시간으로 추천되는 것 처럼 보이는 방법을 사용할 수 있음

현재 서비스는 RDB로 충분히 가능할것으로 생각되고, 만약 문제가 발생한다면 Kafka로 변경할 수 있도록 추상화하여 구현하면 나중에라도 크게 문제가 되지 않을 것 같다고 생각된다.
