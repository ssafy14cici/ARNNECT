# 깃 브랜치 전략

# 방식

1. git-flow 전략
2. github-flow 전략

## 1. git-flow 전략

기본적인 브랜치 구분

```
feature > develop > release > hotfix > master
```

- **메인 브랜치 : master, develop**는 항상 유지
- **보조 브랜치 : feature, release, hotfix**는 ****merge되면 사라짐

### git-flow 브랜치 구조

- master: 라이브 서버에 제품으로 출시되는 브랜치.
- develop: 다음 출시 버전을 대비하여 개발하는 브랜치.
- feature: 추가 기능 개발 브랜치.develop브랜치에 들어간다.
- release: 다음 버전 출시를 준비하는 브랜치.develop브랜치를release브랜치로 옮긴 후 **QA, 테스트**를 진행하고master브랜치로 합친다.
- hotfix: master브랜치에서 발생한 버그를 수정하는 브랜치.

### 흐름

`feature` → `develop` → `release` → `master`

`hotfix` → `master`

## 1. GitHub Flow 전략

기본적인 브랜치 구분

```
feature (or fix) > master
```

- **메인 브랜치 : master**는 항상 유지
- **작업 브랜치 : feature / fix / chore** 는 merge 후 삭제

---

### GitHub Flow 브랜치 구조

- **master**
    - 항상 배포 가능한 상태를 유지하는 브랜치
    - 라이브 서버 기준 브랜치
    - 직접 커밋 금지, PR을 통해서만 merge
- **feature / fix / chore**
    - 기능 개발, 버그 수정, 기타 작업용 브랜치
    - master에서 분기
    - 작업 완료 후 PR을 통해 master으로 merge

---

### 흐름

```
feature (or fix)
        ↓ PR
master(merge = 배포)

```

---

### 특징 요약

- develop, release 브랜치 없음
- PR이 품질 관리의 중심
- master 머지 시 자동 배포 (CI/CD 연계)
- 브랜치 수가 적어 관리가 단순함

---

### 사용 적합 환경

- 웹 서비스
- 잦은 배포
- CI/CD 파이프라인이 구축된 프로젝트
